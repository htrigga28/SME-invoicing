Platform experience hardening

Fix verified defects, then make payment work easier to read.

This plan repairs root setup, unstable throttle tests, mobile overflow, unnamed invoice controls, and split branding. It then adds bounded attention hierarchy, truthful product proof, and one restrained GSAP motion system.

Preserve Lumina. Do not redesign it.

Use the current dark graphite field, lime signal, financial state colors, Hanken Grotesk, JetBrains Mono, and existing product components.

Move from a working demo to a dependable product path.

The target state reduces developer setup friction and owner decision friction. It does not add a new business rule, API contract, or database migration.

Current verified behavior

  • Root database commands miss root .env.
  • Seed deletes demo receipts and payments, then a global backfill can create new IDs, tokens, sequence values, and audit rows.
  • Full API concurrency times out two real HTTP tests, but a serial pass alone does not prove the cause.
  • Long references widen the mobile dashboard.
  • A fixed mobile action can cover status content.
  • Invoice spin buttons have no unique names.
  • Product and onboarding surfaces still show old names or SI.
  • Marketing uses motion; product motion is absent.

Accepted target

  • One explicit API root environment loader with a tested configuration matrix.
  • One guarded, scoped, transaction-safe seed with stable repeat snapshots.
  • Measured throttle policy based on CI-like concurrency, CPU, duration, and handle evidence.
  • Full references wrap inside the viewport.
  • One action is in-flow on mobile and fixed on desktop.
  • Every line-item control has a stable unique label.
  • Lumina continues from onboarding through public documents.
  • GSAP is the only general animation library with lifecycle tests.

The plan resolves the three open choices.

The seed path, animation migration, and dashboard attention treatment have implementation choices. No blocking product question remains.

Phase 1 · Fix setup, scoped seed safety, and measured test scheduling

Files

  • apps/api/jest.config.cjs
  • New apps/api/src/public-rate-limits.spec.ts

Work

  1. Load the root .env from a loader-file path. Test source and compiled commands from root and package cwd.
  2. Let process values win. Test missing file, production mode, missing opt-in, and secret-free logs. Do not add a config package or shell wrappers.
  3. Require non-production mode and ALLOW_DEMO_SEED=true before a demo write transaction.
  4. Wrap demo writes in one transaction scoped to the fixed demo organisation. Never delete payments, events, receipts, invoice events, or audit logs. Upsert by deterministic keys.
  5. Generate missing demo receipts inside that transaction through the existing receipt path. Add an audit row only for a newly created receipt.
  6. Require an explicit organisation for standalone backfill. It must reject empty scope and never scan every successful payment.
  7. Run a non-demo sentinel snapshot before and after two seed runs. Preserve demo IDs, public tokens, sequence values, and receipt audit counts.
  8. Move only two HTTP throttle tests into one file. Preserve forwarded IP checks, 201, 429, and finally cleanup.
  9. Measure default, --maxWorkers=2, --maxWorkers=50%, and --runInBand with CI=true using one representative run per mode. Record wall and per-file duration, CPU, worker count, and handles. Use --detectOpenHandles once on a failing mode.
  10. Add a worker cap only when repeated evidence proves contention. Otherwise fix the confirmed lifecycle defect. Never increase testTimeout, add retries, or suppress failures. After selecting a policy, run the full API suite five consecutive times only at that policy.

Exit

  • Root migration, test migration, seed, scoped backfill, and reconciliation read the root environment.
  • Production or missing-opt-in seed exits before writes.
  • Two seed repeats preserve IDs, tokens, sequence, and audit counts. A sentinel organisation is unchanged.
  • Five API suites pass only at the selected measured policy with the default timeout.
  • No secret appears in captured logs.

Phase 4 · Migrate to restrained GSAP motion

Files

  • Marketing and web package manifests
  • pnpm-lock.yaml
  • Delete marketing motion adapter
  • Marketing hero, header, connected trail, outcomes, and tests
  • Web dashboard, invoice form, tests, and CSS

Rules

  • Import GSAP inside client-only effects or a client-only module. Never register GSAP or ScrollTrigger during server render.
  • Use gsap.context() and revert(). Register ScrollTrigger only where used.
  • Keep the motion-preference helper app-local and inline in each application; do not add a shared animation framework or provider. On a preference change, kill and revert active timelines, then apply the final state or start the no-preference timeline.
  • Render visible final HTML first. Apply transforms after mount only for no-preference users.
  • For reduced motion, create no timeline and no scroll trigger. Set the final state immediately and keep it after a runtime preference change.
  • Keep most motion from 160 to 420 milliseconds. Do not animate large layout or blur fields.
  • Do not add global reveals, parallax, marquees, bounce, or repeating decorative pulses.
  • Do not delay click, submit, focus, error, or navigation behavior.

Accepted surfaces and lifecycle tests

  • Marketing: one hero sequence, one trail progress, incoming outcome state, menu entrance, and incoming preview. Prefer GSAP core or a native scroll signal for trail progress; use ScrollTrigger only when demonstrated parity or lifecycle need requires a continuous trigger.
  • Product: one successful dashboard attention update, one added invoice row, and its related total change.
  • Remove all motion/react imports and dependency entries. Both apps use GSAP, with no second general animation library.
  • Mount components in React Strict Mode, unmount, remount, and change routes. Assert contexts revert, ScrollTriggers are killed, and no stale transforms or listeners remain.
  • Toggle reduced motion while mounted. Assert that no timeline or trigger is created while reduced motion is active.
  • Exit when reduced motion has identical content and action access and tests show no timer leak.

Deterministic lifecycle

  1. Create a unique, narrow database target. Refuse a blank or broad target.
  2. Build with final public URLs. Then migrate and run the guarded seed twice.
  3. Snapshot demo and sentinel IDs, tokens, sequence, and audit counts.
  4. Start built API on 4100, product on 3100, and marketing on 3102. Capture logs.
  5. Health-check API /health and both built roots before Playwright.
  6. Run Playwright with explicit base URLs. Save traces and screenshots.
  7. On failure, print log paths without secrets. In finally, stop processes, close handles, and drop only the unique database.
  8. Run the complete lifecycle twice. A missing prerequisite fails the command.
  9. CI keeps unit and build checks normal. pnpm test:e2e is a local/release gate run twice; do not promise or add a dedicated CI E2E job in this scope unless infrastructure and workflow scope are explicitly provisioned later.
